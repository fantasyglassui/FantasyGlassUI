# Quest Planner, Batch 5 (with others and outside the game) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **This plan is built for parallel execution**: Task 1 runs first and alone; Tasks 2–6 run in three groups (A, B, C), each in its own git worktree at the same time; Task 7 merges them and checks everything. Read "Parallel build and merge" before starting.

**Goal:** The plan reaches past your own screen: a ready-made "LFG" line in your chat box when the plan reaches a group quest (you send it yourself), a duo mode where two add-ons plan one route that fits both players and follow it together, and a plan code you paste on a page of the website that draws the route, gives a checklist for your phone, and adds up the totals.

**Architecture:** One short sequential task adds the seams no group may add itself: two new planner hook points (`"candidate"`, `"replan"`), three new empty files, three settings sections, the fences in Core.lua and smoke.py, and a fixture string handed to the smoke harness. Each group then builds its feature in **its own new file** (A `PlannerGroup.lua`, B `PlannerDuo.lua`, C `PlannerCode.lua` plus the hidden website page), registering only with the batch 4 seams (`ns.PlannerHook`, `ns.GuideRegister*`) and the two new ones, so the groups touch disjoint files except for their own fenced regions.

**Tech Stack:** Lua 5.1 (WoW Forever, interface 16001), the add-on's helpers (`ns:ShowList`, `ns:ShowCopyBox`, `ns:CreateCheckbox`, `ns.ShareChunks`, `ns.ParseSharePiece`, `ns.ShareReceive`, `ns.GroupShortName`, `ns:MessagingLocked`), `C_ChatInfo.RegisterAddonMessagePrefix` / `SendAddonMessage` / `CHAT_MSG_ADDON`, `ChatFrameUtil.OpenChat`; the site in `site-src/` (Python build, plain JavaScript), Node 22 for the reader check; tests in `tests/smoke.py`.

**Spec:** `specs/2026-11-21-quest-planner-design.md`, **Build order, batch 5**: items #31, #35, #44 (and the Tests section's fourth, fifth and sixth rounds for them). Earlier plans and notes in `specs/plans/` (`*-core*`, `*-stops*`, `*-choices*`, `*-feel*`).

## Global Constraints

- Everything in batches 1–4's Global Constraints still binds: Forever audit; `luacheck . -q` 0 warnings; smoke.py `errors: no errors` twice; never plan in combat; 4 ms slices; `ns.PlannerYield()` only in plain loops (never inside `pcall`/`Try`, a sort comparator or a gsub callback); all phrases in 9 languages; Questie read-only through pcall; everything behind `ns:GuideUnlocked()`; nothing about the planner in /fgui help, README, wiki or changelog; commits by DustyMouse (`git -c user.name=DustyMouse -c user.email=fantasyglassui@users.noreply.github.com commit`) with no attribution lines; implementers never push.
- **The unlock phrase is never written anywhere** (code, tests, plan, notes, commit messages). Tests unlock with `ns.GuideUnlocked = function() return true end`.
- **No `ReloadUI` in planner code** (the game refuses it from add-on code on this client): `grep -n ReloadUI FantasyGlassUI/Planner*.lua` stays empty.
- **Nothing about the planner on the public site.** `docs/` is not changed by this batch at all. The plan page (#44) is built only when `site-src/build_site.py` is run with `--plan`, which nobody does in this batch; a plain build writes exactly what it wrote before. Even with `--plan` the page is not linked from any page, not in `sitemap.xml`, not in `robots.txt`, carries `<meta name="robots" content="noindex, nofollow">`, no canonical/hreflang, no structured data and no visit counter, and shows nothing but a paste box until it is given a plan code. Its words live in its own `site-src/plan/words.json`, never in `site_tr.py`, `keys_*.json` or `docs/i18n`. Its source never uses the word "planner" (it is "the quest guide's plan"), so batch 4's release grep over `site-src` stays valid. Pinned by `tests/sitecheck.py` (Task 6) and Task 7.
- **Messages between players (duo; #31 sends none):** only through `C_ChatInfo.SendAddonMessage` with the prefix `ns.PLANNER_DUO_PREFIX = "FGUIPlan"`, registered once (`C_ChatInfo.RegisterAddonMessagePrefix`, through pcall) when the guide is unlocked (at PLAYER_LOGIN, and on unlock); always `"WHISPER"` to the one partner, never PARTY/RAID/GUILD/channels, **never anything in public chat** (`SendChatMessage` is never called by planner code). Every send goes through one queue: at most one message every 0.25 s, each ≤ 255 bytes, plan and state text in `ns.ShareChunks` pieces (200 characters); the queue holds while `InCombatLockdown()` or `ns:MessagingLocked()` (inside an instance), and resumes after. A result of `Enum.SendAddonMessageResult.AddonMessageThrottle`/`ChannelThrottle` retries the same message after 2 s (3 tries, then the duo ends with a message); `TargetOffline` ends the duo ("%s is offline: planning for you alone."). No value is sent unless it is a plain number or string that `ns:IsSecret` says is readable. Incoming: ignored unless prefix, channel and text are readable strings, the prefix is ours, the channel is `"WHISPER"`, the sender (`ns.GroupShortName`) is the partner (or, for an invitation, anyone), and the session id matches; nothing incoming is ever executed (texts are parsed by patterns and `ns.GuideParseLine`).
- **#31 sends nothing.** The line goes into your chat box with `ChatFrameUtil.OpenChat`; you press Enter yourself. A test spies `SendChatMessage`, `C_ChatInfo.SendChatMessage` and `C_ChatInfo.SendAddonMessage` and expects 0 calls.

- Settings stay on the Guide tab. New switches: `plannerFindGroup` "Find a group button" (default true), `plannerLFGChannel` (default `""` = your chat box's current channel), `plannerDuoAsk` "Let friends ask to plan with you" (default true).

### Rulings (the spec leaves these open)

- **Seams first.** Task 1 adds the hook points the duo needs in Planner.lua, so no group edits Planner.lua, PlannerRoute.lua or Guide.lua.
- **#31 sends no add-on messages.** The task brief lists "find a group" among the add-on-message features, but the spec says "The add-on never sends it": find a group only fills your chat box. The message rules above bind the duo only.
- **Find a group (#31):** it shows when the step you are on is a step (`accept`, `do`, `turnin`) of a quest that needs a group, `ns.PlannerNeedsGroup(questID) -> "elite"|"group"|"dungeon"|nil` (from the source's record `elite`/`group`/`dungeon`, cached per session; it is worked out when the panel is drawn, so it works on a reloaded plan and on the duo friend's plan), the planned guide is followed, `plannerFindGroup ~= false`, the group setting is not Solo (or you are the duo friend: the leader's setting made the plan), and you are not in a full party (`GetNumGroupMembers() >= 5`) or a raid. It is a panel line "Group quest: %s" plus a panel action and a step action "Find a group". The line is `format(ns:Tr("LFG %s, %s"), title, zone)` (`"LFG %s"` with no zone), the title cleaned of `|` escapes and control characters, the whole ≤ 200 bytes. "The channel you pick": `plannerLFGChannel` names a channel you have joined (the Guide tab cycles "Chat box" and the names `GetChannelList()` gives); at click time `GetChannelName(name)` gives its number `n` and the line starts `"/n "`; not joined → no prefix and "You are not in %s: the line is in your chat box for its current channel." Without `ChatFrameUtil.OpenChat` the line is printed for you to copy.
- **Duo (#35), who and how:** "Plan with a friend" (panel action, `/fgui guide duo [name]`) asks your target when it is a friendly player, else your only party member, else the name given; no one → "Target your friend or group with them, or type /fgui guide duo <name>." The friend's add-on shows `ns:ShowList("PlanDuoAsk", "Plan with a friend", ...)` with "%s asks to plan your route together." and the clickable "Plan together" / "No thanks"; `plannerDuoAsk == false`, a locked guide or no choice in 60 s → no answer. A locked friend sends nothing at all, so nobody learns the planner is there.
- **Duo, the friend's state:** `{ level, faction, class, questie, log = { [id] = { done, total } }, can = { [id] = true }, flights = { [node] = true }, hearth = { map, x, y, ready } | nil }`. `can` is the friend's own `ns.PlannerCandidates` result (all three lists) with `ctx.group = "all"` (the leader's group setting decides), worked out as a `ns.PlannerJob` (sliced); at most 300 ids. With no Questie on the friend's side (`questie = false`) the leader plans only quests both have in their logs, and says once "%s has no Questie: planning the quests you both have." A level that can't be read is not sent; it is tried again every 5 s, 6 times, then "Could not read your level: try again out of combat."
- **Duo, the plan fits both:** while leading with a state: the level window is `[max(level, friend) − 4, min(level, friend) + 2]` (levels more than 6 apart: "You are %d levels apart: planning together needs 6 or fewer. Planning for you alone." and the duo ends); a quest is kept only when it is in the friend's log or `can` (or, without Questie, in both logs), the leader's own logged quests included; a flight point counts as known only when both know it (so the plan may add `learnflight`; whoever already knows it ticks it at once); the hearthstone is used only when the friend's is ready and bound within `ns.PLANNER_HUB_YARDS` of yours. The experience and pace are the leader's.
- **Duo, the shared plan:** after each applied plan the leader sends the guide's text (`ns.GuideText`) with a first comment line `# duo <session> <planId> <zone> <fromLevel> <toLevel>`; the friend parses it with `ns.GuideParse` (at most 80 steps; a line that does not parse throws the whole plan away) and follows it through `ns:GuideSetPlan(guide, { zone, fromLevel = own level, toLevel = own level, duo = leader })`, applied after the fight when one arrives in combat. Only the leader plans: the friend's `"replan"` hook refuses every replan and instead sends its state (debounced 2 s) so the leader replans with it; the friend's own "Plan my route" (`reason == "start"`) ends the duo and plans alone. Following a written guide on either side ends it.
- **Duo, progress and waiting:** each side sends `D1:AT:<session>:<planId>:<at>:<n>` when its step changes (the advance hook). Panel line: partner's `at` past yours (or past the end) → "%s: done"; same → "%s: on this step"; behind → "%s: %d steps behind". When your step is `turnin`, `fly`, `sail` or `hearth` and the partner is behind, the line is "Wait for %s here" instead (it does not stop the step ticking). A partner's step for another planId is not shown. Title part on both sides: "with %s".
- **Duo, staying in touch:** `D1:HI` every 60 s while out of combat and not locked; no message from the partner for 300 s (counted only while your own messaging is not locked) → "Lost touch with %s: planning for you alone." and the duo ends (the friend goes back to its own planner with `ns:PlannerStart()`). Inside an instance the panel line is "Planning together is paused inside an instance."
- **Plan code (#44):** `"SUIP1!"` followed by the add-on's share encoding (the one theme codes use: `S<bytes>:text`, `N<number>;`, `{ key value ... }` with keys sorted by `tostring`), of `{ v = 1, lv = { from, to }, xp, s, fl = flights, cr = crossings, z = { { m = uiMapID, n = name } }, st = { { k = kind, t = text, z = zone index|nil, x, y } } }`: steps in plan order, `t` = `ns.GuideStepBase(step)` cleaned of `|` escapes and control characters, at most 80 bytes; x and y rounded to one decimal; one zone per distinct step map (`C_Map.GetMapInfo(map).name`, at most 40 bytes); at most 60 steps (`more = n` counts the rest); numbers rounded to whole numbers except x, y. "Share plan" (panel action, `/fgui guide share`) opens `ns:ShowCopyBox(code, ns:Tr("Copy this plan code and paste it on fantasyglassui.com/plan/"))`.
- **The page (#44):** one page with every language inlined (chosen from `navigator.language`, with a language picker); a code is pasted, or given in the URL **fragment** (`#c=<code>`, never the query string, so it never reaches a server). It shows the totals ("Experience", "Time", "Levels 24 → 26", "Flights", "Crossings"), one SVG panel per zone (labelled with its name, stops placed by x, y on a 100×100 box, numbered, joined by a solid path; `fly`/`sail`/`hearth` legs drawn dashed between panels and marked with a small icon text "F", "S", "H"), and a checklist of every step with a checkbox kept in `localStorage` under `"fgui-plan-" + hash(code)` (every read and write in try/catch), and "Clear the ticks". No `fetch`, `XMLHttpRequest`, `sendBeacon`, `WebSocket`, external script, stylesheet, font or image; the site's font comes inline from `marcellus.b64`.
- **Plan codes tested on both sides:** `tests/plan_codes.txt`, one case per line, tab separated: `ok<TAB>steps<TAB>zones<TAB>xp<TAB>kinds(comma)<TAB>code` or `bad<TAB>why<TAB>code` (`why` ∈ `empty`, `kind`, `damaged`, `version`). smoke.py hands its text to the harness as `planCodes`; the Node check reads the same file.

## Review Focus

- **The friend has no add-on, an old one, or a locked guide**, or is offline: no answer within 30 s → "No answer from %s (offline, or no Fantasy Glass UI): planning for you alone." and a normal solo plan; nothing shown on the friend's side; no error. → Task 3 test.
- **Messages from a third player, malformed or oversized pieces, a piece count over 400, a plan or step for an old session or planId** → ignored, nothing applied, no error. → Task 3 and Task 4 tests.
- **A fight or an instance starts in the middle of sending a plan**: nothing is sent while locked, the rest follows after, in order, and the friend applies the plan only after its own fight. → Task 3 and Task 4 tests.
- **A damaged, truncated, empty or other-kind code** (a theme code `SUIT1!`, a layout code) pasted on the page, and a plan whose steps have no place (`note`) or whose zone has no stops → a clear message or a checklist entry without a dot, never an exception. → Task 5 fixture lines, Task 6 Node check.
- **A quest title with `|` escapes, a colour code or 200 characters, or no zone** in find a group → a clean line within 200 bytes; no `ChatFrameUtil` → the line printed. → Task 2 test.

## Parallel build and merge

1. The controller runs **Task 1** on `quest-planner`, reviews it, runs **one fix round** for its findings, and commits. Call that commit `SEAMS`.
2. Three worktrees from `SEAMS`, built at the same time, one implementer each:
   `git worktree add ../fgui-together-a -b together-a SEAMS` (and `together-b` in `../fgui-together-b`, `together-c` in `../fgui-together-c`). Group A: Task 2. Group B: Tasks 3 then 4. Group C: Tasks 5 then 6.
3. Review: when a group's last task is committed, one reviewer reviews **the whole group** (`git diff SEAMS..together-<x>`) against this plan; the group's implementer then makes **one combined fix round** for every finding of that review (one commit, `"Planner: batch 5 <x> review fixes"`), not one per task.
4. Rules for every group, so the merge is mechanical:
   - Touch only the files its tasks list. In a shared file, write only between its own region's two fence lines (Core.lua, smoke.py) or inside its own section function's body (Bars.lua). Never move, reword or delete a fence or another group's lines.
   - New add-on phrases go to `specs/plans/phrases/together-<x>.json`, not Locales.lua.
   - Use another group's function only through a guarded call (`if ns.PlannerDuoRole then ... end`) and stub it in your own test; Task 7 checks the real pairing.
   - Every smoke test restores every global and `ns` field it changes (the `saved = {...}` / `pcall` / restore pattern) and removes every hook it registers, so the regions can run in any order.
5. **Task 7** (controller, on `quest-planner`): `git merge --no-ff together-a`, then `together-b`, `together-c`. A `.luacheckrc` conflict is resolved by `python3 site-src/tools/regen_rc.py`; a conflict anywhere else means a group wrote outside its region: keep both sides in region order (A, B, C) and note it in the batch notes. Then `git worktree remove` the three worktrees and delete the branches.
